1. Benchmark Analysis:
The Nbody benchmark simulates the movement of the planets (sun, jupiter, saturn, uranus, neptune) to test how well Python handles heavy math and loops.
It uses only basic python math operations and avoids external heavy libraries like NumPy.
For data structures, it uses basic python lists, with each body represented as object containing seven floating point variables: 3D position, 3D velocity, and mass. 	
	
The algorithm uses basic physics to calculate the gravity between every pair of bodies (O(n^2)), updating their positions step by step.
Because it checks every pair, the main bottleneck will likely be the inner loop that updates these forces.
Since this loop runs millions of times, just accessing the object variables creates a lot of overhead in Python.
In addition, doing floating-point math and calculating square roots sequentially is really slow.
	
2. Detecting Bottlenecks
As we can see, the perf report and the Flame Graph immediately point to the same major issue: Python's interpreter overhead.
In the perf report, we can see that _PyEval_EvalFrameDefault consumes 44.76% of the total runtime.
In the Flame Graph, it appears as a massive vertical stack and a wide base dedicated entirely to frame evaluations.
both of these results make it clear that the script spends most of its execution runtime inside Python's internal interpreter loop.
   
In addition, the perf report reveals more bottlenecks:
- heavy floating-point math operations such as:
	- float_mul (6.18%)
	- float_sub (3.01%)
	- float_add (3.00%)
 that runs in the physics calculation inside the O(n^2) loops
- frequent object memory management overhead shown by float_dealloc (5.12%) that is caused by python keeping everything as object structures.
   - continuous list modifications or lookups like:
     - list_ass_subscript (3.95%)
	 - list_subscript (2.73%)
	that are caused because the basic list use
	 
3.	Optimization
we rewrote the code using NumPy arrays and vectorization to completely eliminate slow Python loops. Instead of iterating through
planet pairs one by one, we packed all the positions, velocities, and masses into flat, contiguous blocks of memory.
we broke it down into three concepts:

 -Contiguous Memory Layout: Standard Python lists are arrays of pointers scattered across RAM, 
  forcing the CPU to waste time chasing pointers.NumPy stores data sequentially in continuous memory blocks, allowing the CPU to pre-fetch          data.

 -Vectorized Operations and Indexing: Instead of cusing slow 'for' loops, we used np.triu_indices to grab all planet pairs at once.
  This enables us to calculate coordinate differences and velocity updates
  for all arrays at once in a single operation.

 -C Level Execution: Even though the code is written in Python, 
  the heavy math is offloaded to pre-compiled C libraries running inside NumPy.
  This completely skips the slow Python interpreter (PyEval_EvalFrameDefault) and 
  stops the creation of temporary heap objects (float_dealloc)
