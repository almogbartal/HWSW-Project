1. Benchmark Analysis:
The Nbody benchmark simulates the movement of 5 bodies (planets): sun, jupiter, saturn, uranus and neptune, calculating the gravitational pull between them.
It uses basic python arithmetic operations and doesn't use external numerical libraries like NumPy for the actual N-body calculations.
It uses basic python data structures, with each body represented by a tuple containing a 3D position list, a 3D velocity list, and a floating point mass. 	
	
The algorithm calculates the gravity between every pair of bodies (O(n^2)), updating their positions step by step.
Although there are only 5 bodies (which makes 10 unique pairs), every pair's calculation is repeated in many iterations inside the loop.
Since these calculations repeat many times in the loop, we expect the loop to be a bottleneck.
In addition, for every iteration, the loop does sequential floating-point math (subtraction, multiplication, power/square root), and repeatedly accesses and modifies the list elements using indexing, which probably creates a lot of overhead in python.

2. Detecting Bottlenecks
As we can see, the perf report and the Flame Graph immediately point to the same major issue: Python's interpreter overhead.
In the perf report, we can see that _PyEval_EvalFrameDefault consumes 44.76% of the total runtime.
In the Flame Graph, we can see it, as _PyEval_EvalFrameDefault occupies a large portion of the graph (with a wide base and high stack).
Both of these results make it clear that the script spends most of its execution runtime inside Python's internal interpreter loop, making the interpreter itself the main bottleneck.
   
In addition, the perf report reveals more bottlenecks:
-floating-point operations:
	- float_mul (6.18%)
	- float_sub (3.01%)
	- float_add (3.00%)
which come from the repeated gravity calculations and coordinate updates.
- frequent object memory management overhead shown by float_dealloc (5.12%) that is caused by python constantly creating and destroying temporary float objects during calculations.
   - continuous list modifications or lookups like:
     - list_ass_subscript (3.95%)
	 - list_subscript (2.73%)
	that are caused by repeatedly accessing and updating coordinates like v1[0] and r[0].
	 
3.	Optimization
To reduce execution time in the N-body benchmark, three main approaches were evaluated:
-Micro-optimizations: Manual loop unrolling and math calculations in pure Python gave minimal 
 improvments and sometimes ran even slower due to extra interpreter overhead.

-Vectorization (NumPy): NumPy (a Python library for fast array calculations) provided no real 
 improvement here and often ran slower than the baseline. Creating temporary arrays and switching
 between Python and C code overhead outweighed any vectorization benefits.

-JIT Compilation (Numba):  Just-In-Time compilation via numba was adopted as the final solution. 
 This is a Python tool that converts code into fast machine language on the go which resolved the CPU bottleneck.
 By compiling the O(n^2) interaction loops directly into native low-level VM machine code at runtime, it bypassed 
 bytecode interpretation and  object allocation overhead resulting in:

  -Mean Execution Time: Dropped from 237 ms down to 3.11 ms with Numba JIT, achieving a 76.2 times speedup (98.69 % runtime reduction).

  -Interpreter Overhead (_PyEval_EvalFrameDefault): Reduced from 44.76% total runtime in the baseline down to 11.17% in the optimized version.  

  -Floating-Point Operations Overhead: CPython wrapper overheads for floating-point math—float_mul (6.18%), float_sub (3.01%), and float_add (3.00 %), which totaled 12.19% in the baseline—were reduced to 0.00% as calculations moved directly to hardware FPU registers.

  -Object Allocation Overhead (float_dealloc) : Memory management overhead from repeatedly creating and destroying Python float objects dropped from 5.12% in the baseline down to 0.00% in the optimized code.

  -List Access Overhead : Dynamic list access overheads, which consumed 6.68% of baseline execution time, were reduced to $0.00% by switching to contiguous C-array buffer pointers.

Some metrics where the optimized version performed worse were s following:
  -Page Faults: Increased from 117,757 to 385,005 due to LLVM dynamic code compilation and memory allocation during the JIT warmup phase.

  -Branch Mispredictions: The miss rate increased from 0.64% in the baseline to 2.24% in the compiled native code.

  -Total Harness Elapsed Time: Total benchmark sampling task-clock time was higher 46,416.77 ms vs 24,711.13 ms, due to the initial JIT compilation overhead during startup.
